## 一、產品定義

**定位（README 第一行）**
> 基於 ppt-master 的職場簡報工作流——**頁型用挑的、動畫用點的、單頁重做不用等全份。**

**歸屬聲明（README 緊接其後）**
> 本專案使用 [ppt-master](https://github.com/hugohe3/ppt-master) (MIT) 的 SVG → 原生 PPTX 編譯引擎，
> 在其上新增：職場頁型庫、動畫選擇器、單頁重生成、繁體中文介面。

**核心主張**：三個新功能是同一件事——**把控制權從 AI 手上還給使用者**。頁型庫＝版面選擇權，動畫選擇器＝動效選擇權，單頁重生成＝修改粒度。這正好打在 ppt-master 的結構性弱點：AI 全權決定、使用者只能事後用文字拉扯。

**關係定位**：非競爭。小型開源工具 ＋ 職場向內容題材。

## 二、架構決策

| 項目 | 決策 |
|---|---|
| repo 形態 | 獨立 repo，**不 fork** |
| 引擎 | vendor `ppt-master`（MIT，鎖定版本快照），目錄保持**原封不動、可整包替換** |
| 客製化形態 | **覆蓋層架構**——自己的改動全部是「加法」，放在獨立目錄 |
| 例外 | 單頁重生成必須 patch 引擎內部，是唯一破例（故排在最後階段，風險隔離） |
| open-slide | **剪掉**。設計思路已吸收（選取狀態通道），程式碼一行不用——React/Vite 生態與 Python 引擎不相容，移植等於重寫 |

## 三、v1 功能規格

### 3.1 頁型庫（4 個）

形態：**骨架 ＋ 槽位契約**——每個頁型 = 可渲染縮圖的 SVG 骨架（定義區塊與槽位）＋ 依內容量伸縮的規則。

| 頁型 | 彈性範圍 | 備註 |
|---|---|---|
| 對比頁 | 固定 2 欄 | 引擎已有 `comparison_matrix` / `feature_matrix` 可複用 |
| SWOT | 固定 4 象限 | 引擎已有 `matrix_2x2` 可複用 |
| KPI 儀表板 | **3-6 個指標**（超過建議拆頁） | 引擎已有 `gauge` / `bullet` / `progress_bar` |
| 流程圖 | 節點數彈性（**建議 3-7，待確認**） | ⚠️ 引擎硬規則「no Structure catalog」，流程圖被刻意設計成每次即席手繪——這是四個裡最需要新開發的 |

指定方式（兩種並存）：
- **生成前配額**（零開發）：需求裡說「幫我做一頁 SWOT」，AI 規劃時採用
- **生成後替換**（v1 目標）：預覽編輯器裡對任一頁換頁型 → 單頁重生成

### 3.2 動畫選擇器

引擎已有 203 個效果的機器可讀註冊表 `scripts/pptx_animation_presets.json`（進場 53、強調 33、路徑 64、退場 53），但確認頁只有一個布林開關——**能力存在，介面缺失**。

兩層設計：
- **Deck 套組（主）**：3 套預設（專業沉穩／輕快活潑／極簡無干擾），一鍵套用整份
- **元素微調（輔）**：預覽編輯器裡點元素改效果與順序；選單**每類只放 6-8 個常用**，不是全部 203
- **差異化賣點**：即時預覽**單一元素**的動畫（PowerPoint 必須播放整頁才看得到）

### 3.3 單頁重生成

預覽裡改一頁 → 只重跑該頁 → 重新匯出。引擎目前是全量重跑重匯出。**必須 patch 引擎流程**，不確定性最高。

### 3.4 繁體中文化

**707 個中文 UI 字串**（v4.5.0 實測），集中在 3 個檔案：

| 檔案 | 字串數 |
|---|---|
| `confirm_ui/static/app.js` | 345 |
| `confirm_ui/static/catalogs.json` | 223 |
| `svg_editor/static/app.js` | 139 |

Server 與 HTML 零硬編碼中文，i18n 結構乾淨（`svg_editor` 已有 en/ja/zh 字典）。做法：OpenCC `s2twp` 自動轉換 ＋ 人工校對台灣用語。**成果 PR 回上游**（純加法、爭議最小、最易被接受；被接受後連覆蓋層都省了）。

### 3.5 零開發的「露出」工作

引擎已存在但使用者看不到的東西，只需在繁中面板上曝光：18 種視覺風格、5 種敘事模式、33 個圖表模板、6 個表格模板、7 套版面系統、`create-template` 品牌工作區。

## 五、執行順序與階段驗收

**順序原則：難度遞增，且前面的工作是後面的偵察。**

| 階段 | 內容 | 驗收標準 | 預估 |
|---|---|---|---|
| **1** | 繁中化 707 字串 ＋ 上游 PR | 面板全繁中、腳本掃不到簡體殘留、PR 已送出 | 1 session |
| **2** | 頁型庫 4 個 | 需求可指定頁型、產出頁通過 `svg_quality_checker`、縮圖可預覽 | 1-2 sessions |
| **3** | 動畫選擇器 | 套組可選、元素可微調、單元素動畫可即時預覽、匯出 pptx 動畫行為正確 | 1-2 sessions |
| **4** | 單頁重生成 | 預覽裡換頁型只重跑該頁，耗時 < 全量的 1/3 | 2-3 sessions |

階段 1 同時是偵察：讀完 717 個字串等於摸熟 `confirm_ui/app.js` 與 `svg_editor/app.js` 的架構，而那正是階段 3 要動刀的地方。

**真正的瓶頸不是寫程式碼**，是 (1) 讀懂別人 16,000 行前端的 context 成本 (2) UI 必須人工點過才知道對不對的往返 (3) 階段 4 patch 引擎的不確定性。

## 附：內容素材（已就緒的鉤子）

1. **「憑想像寫的 skill」**——`openslide-ppt-skill` 對著不存在的 API 編譯，單一 commit，README 安裝指令指向另一個帳號。教訓：把設計約束放 prompt 而非型別系統，任何人都能寫出「表面看起來對」的 wrapper 而無人察覺。
2. **規範稅 5,100 行**——ppt-master 跑一次標準流程要載入 15 份規範才畫第一頁；全庫 212 個 markdown、29.4 萬字。
3. **驗證器 > prompt 紀律**——同一條防爆版規則，ppt-master 寫成可執行 checker（實跑抓到 5 處溢界），open-slide 寫成 31 行叫模型心算，超出畫布靜默裁切、零偵測。
4. **兩個工具的共同盲點**——AI 全程盲畫，沒有渲染回饋；數學抓得到溢界，抓不到「醜」。
